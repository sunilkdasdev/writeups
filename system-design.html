System Design: Step by Step

A conversational guide to designing systems from scratch. Think of this as a dialogue between you (the engineer) and the system.

Step 1: What Are We Building?

You: "I need to build something. Where do I start?"

System: "Hold on! First, tell me WHAT you're building. Give me requirements."

You: "Okay, it's a URL shortening service like bit.ly."

System: "Got it. Requirements:
- Users submit long URLs, we give them short URLs
- When someone visits short URL, redirect to long URL
- Must handle millions of users"

Key Question: What is the functional requirement? What are the non-functional requirements (latency, throughput, availability)?

Step 2: High-Level Design

You: "Now how do I structure this?"

System: "Let's draw boxes. Three main parts:

1. API Server - handles user requests
2. Database - stores URL mappings
3. Redirect Service - maps short → long URL"

User → API Server → Database
                Browser → Redirect → Long URL

Key Decision: What are the core components? How do they communicate?

Step 3: API Design

You: "What should the API look like?"

System: "Keep it simple:

1. POST /api/shorten - body: {longUrl: "..."}
  returns: {shortUrl: "http://s.ly/abc123"}
2. GET /api/shorten/:id - returns the long URL
3. GET /abc123 - redirects to long URL"

Key Question: What are the endpoints? What are the request/response formats?

Step 4: Data Model

You: "How do I store the URLs?"

System: "Simple table:

idshort_codelong_urlcreated_at
1abc123https://google.com2024-01-01

You: "What database?"
System: "Start with relational (MySQL/PostgreSQL). Move to NoSQL if needed. For this? Any works."

Key Decision: What database? What schema?

Step 5: Capacity Planning

You: "Will this scale?"

System: "Let's calculate:

- 1 billion URLs
- Each URL ~100 bytes + overhead = ~150 bytes
- Storage: 1B × 150 bytes = 150GB

Read QPS (queries per second):
- 10M visits/day = ~100 QPS average
- 10x for peak = ~1000 QPS

Key Question: What's the storage? What's the QPS?

Step 6: Caching

You: "Database will get hit hard!"

System: "Yes! Add cache:

1. Check Redis/Memcached first
2. If miss, query database
3. Store in cache, return

Use 80/20 rule:
- 80% traffic goes to 20% popular URLs
- Cache those!"

Key Decision: What to cache? Eviction policy?

Step 7: Load Balancing

You: "One server won't handle all traffic!"

System: "Right! Add load balancer:

Users → LB → Server1
                    → Server2
                    → Server3

Options: Round Robin, Least Connections, IP Hash

Key Decision: How to distribute? What algorithm?

Step 8: High Availability

You: "What if a server dies?"

System: "Design for failure:

1. Replication - DB primary + replicas
2. Multi-AZ - across data centers
3. Health checks - detect failures
4. Automatic failover - switch to backup

You: "What's our SLA?"
System: "99.9% = 9 hours downtime/year
99.99% = 53 minutes downtime/year"

Key Decision: What availability level?

Step 9: Short URL Generation

You: "How do I generate the short code?"

System: "Several options:

1. Hash-based: hash(longUrl) → base62
  Problem: hash collisions

2. Auto-increment: DB id → base62(1)
  Problem: predictable, exposes count

3. Random + Check: generate random, verify unique
  Best for URL shorteners!"

Key Decision: How to generate? What encoding?

Step 10: Wrap Up

You: "Anything else?"

System: "Review time:

✓ Flow: User → Short URL → Redirect → Long URL
✓ API: POST /shorten, GET /:id
✓ DB: id, short_code, long_url
✓ Scale: Cache + LB + Replication
✓ Availability: Multi-AZ failover

Now draw it on whiteboard!"

Pro Tips:
- Start simple, iterate
- Don't over-engineer
- Know trade-offs
- Be ready to explain choices

System Design Checklist

  • Requirements - What are we building?
  • High-Level Design - Core components?
  • API Design - Endpoints?
  • Data Model - Schema?
  • Capacity - Storage, QPS?
  • Caching - What to cache?
  • Load Balancing - Distribution?
  • Availability - SLA?
  • Generation - Short codes?
  • Trade-offs - What did we compromise?
