Distributed Locking: Implementing Reliable Synchronization in Distributed Systems

Introduction

Distributed locking provides mutual exclusion across multiple processes running on different machines. While local mutexes and monitors work within a single JVM, distributed locks coordinate access to shared resources that span multiple nodes, databases, or even geographic regions.

The need for distributed locking arises in numerous scenarios: preventing concurrent modifications to shared data, coordinating leader election, managing resource reservations, implementing rate limiting, and ensuring that background jobs execute exactly once. This article explores the theoretical foundations, implementation patterns, and production considerations for distributed locking systems.

The Fundamental Challenge

Local locks leverage shared memory—a single CPU core can atomically modify a memory location using hardware instructions like compare-and-swap. Distributed systems lack this shared memory; instead, they must coordinate through a shared storage system that introduces network latency, potential failures, and concurrency complexities.

A distributed lock implementation must satisfy several critical properties. Mutual exclusion ensures that at most one holder owns the lock at any time. No deadlock guarantee (or deadlock detection and recovery) ensures the system can make progress even when participants fail while holding locks. Lock release must be reliable—even if the holder crashes, the lock must eventually be released (through TTL or explicit cleanup). Finally, fault tolerance ensures the lock service remains available despite node failures.

The theoretical impossibility of distributed systems (as expressed in the CAP theorem) means that no lock implementation can provide all properties simultaneously under all failure scenarios. Each implementation makes specific trade-offs that applications must understand and accommodate.

Database-Based Distributed Locks

The simplest approach to distributed locking uses a database table as the lock storage. A lock is represented by a row that processes attempt to insert or update. The success or failure of this operation determines lock acquisition.

Pessimistic Locking with SELECT FOR UPDATE

One approach uses SELECT FOR UPDATE with a condition that can only be satisfied once. A process queries for the lock row with a flag indicating unowned, attempts to update it with its identity, and checks whether the update affected any rows:

public boolean acquireLock(String lockName, String holderId, Duration timeout) {
    // Attempt to claim the lock
    int updated = database.execute(
        "UPDATE distributed_locks SET holder_id = ?, acquired_at = NOW(), " +
        "expires_at = DATEADD(second, ?, NOW()) " +
        "WHERE lock_name = ? AND (holder_id = ? OR expires_at < NOW())",
        holderId, timeout.getSeconds(), lockName, holderId
    );
    
    if (updated > 0) {
        return true;
    }
    
    // Check if we already hold this lock
    Lock lock = database.query(
        "SELECT * FROM distributed_locks WHERE lock_name = ?",
        lockName
    );
    
    return lock.holderId.equals(holderId) && lock.expiresAt.isAfterNow();
}

This approach is pessimistic—it assumes conflicts will occur and prevents them through database concurrency control. The UPDATE operation is atomic; only one process can successfully update the row in each execution.

Optimistic Locking with Version Columns

Optimistic locking uses version numbers to detect conflicts. A process reads the current lock state, attempts to update it with an incremented version, and retries if the version has changed:

public boolean acquireLockOptimistic(String lockName, String holderId) {
    while (true) {
        Lock lock = database.query(
            "SELECT * FROM distributed_locks WHERE lock_name = ?",
            lockName
        );
        
        if (lock == null) {
            // Lock doesn't exist, create it
            database.execute(
                "INSERT INTO distributed_locks (lock_name, holder_id, version, " +
                "acquired_at, expires_at) VALUES (?, ?, 1, NOW(), DATEADD(minute, 10, NOW()))",
                lockName, holderId
            );
            return true;
        }
        
        if (lock.holderId.equals(holderId)) {
            // We already hold the lock, extend it
            int updated = database.execute(
                "UPDATE distributed_locks SET version = version + 1, " +
                "expires_at = DATEADD(minute, 10, NOW()) " +
                "WHERE lock_name = ? AND holder_id = ? AND version = ?",
                lockName, holderId, lock.version
            );
            if (updated > 0) return true;
            // Version changed, retry
            continue;
        }
        
        if (lock.expiresAt.isBeforeNow()) {
            // Lock expired, try to take it
            int updated = database.execute(
                "UPDATE distributed_locks SET holder_id = ?, version = version + 1, " +
                "acquired_at = NOW(), expires_at = DATEADD(minute, 10, NOW()) " +
                "WHERE lock_name = ? AND version = ?",
                holderId, lockName, lock.version
            );
            if (updated > 0) return true;
            // Someone else took it, retry
        }
        
        return false;
    }
}

Optimistic locking works well when conflicts are rare. It performs better than pessimistic locking under low contention but can waste work when many processes compete for the same lock.

Limitations of Database Locks

Database-based locks have inherent limitations. Performance scales with database throughput, which may become a bottleneck for high-frequency lock operations. Database failures can cause complete lock service unavailability. The coarse granularity of database transactions may not provide the fine-grained timing guarantees some applications require.

Despite these limitations, database locks provide a simple, reliable foundation for many use cases. They require no additional infrastructure beyond the database, and their semantics are straightforward to reason about.

Coordination Service-Based Locks

Specialized coordination services like ZooKeeper, etcd, and Consul provide more sophisticated locking primitives. These services are designed specifically for distributed coordination and offer better performance and reliability than database-based approaches.

ZooKeeper Sequential Znodes

ZooKeeper provides sequential znodes that can implement distributed locks. To acquire a lock, a client creates a sequential ephemeral node under a parent lock node. The client then checks whether its node has the lowest sequence number among all children. If yes, it holds the lock. If not, it watches the node with the next-lowest sequence number and waits until it is deleted.

This approach, called the lock file pattern, provides exactly-once semantics and automatic cleanup on client failure (through ephemeral nodes). The following implementation demonstrates the pattern:

public class ZooKeeperDistributedLock implements AutoCloseable {
    private final ZooKeeper zooKeeper;
    private final String lockPath;
    private final String lockName;
    private final String holderId;
    private String myZnode;
    private volatile boolean acquired = false;
    
    public boolean acquire(Duration timeout) throws InterruptedException {
        long deadline = System.currentTimeMillis() + timeout.toMillis();
        
        // Create sequential ephemeral node
        myZnode = zooKeeper.create(
            lockPath + "/" + lockName + "-",
            holderId.getBytes(),
            ZooDefs.Ids.OPEN_ACL_UNSAFE,
            CreateMode.EPHEMERAL_SEQUENTIAL
        );
        
        // Check if we hold the lock
        while (true) {
            List children = zooKeeper.getChildren(lockPath, false);
            Collections.sort(children);
            
            String myName = new Path(myZnode).getFileName();
            int myIndex = children.indexOf(myName);
            
            if (myIndex == 0) {
                acquired = true;
                return true;
            }
            
            // Watch the predecessor
            String predecessor = children.get(myIndex - 1);
            CountDownLatch latch = new CountDownLatch(1);
            
            Watcher watcher = event -> {
                if (event.getType() == EventType.NodeDeleted) {
                    latch.countDown();
                }
            };
            
            zooKeeper.exists(lockPath + "/" + predecessor, watcher);
            
            // Wait for predecessor to be deleted or timeout
            long remaining = deadline - System.currentTimeMillis();
            if (remaining <= 0) {
                // Release our node and fail
                release();
                return false;
            }
            
            latch.await(remaining, TimeUnit.MILLISECONDS);
        }
    }
    
    public void release() throws InterruptedException {
        if (acquired && myZnode != null) {
            zooKeeper.delete(myZnode, -1);
            acquired = false;
        }
    }
    
    @Override
    public void close() throws InterruptedException {
        release();
        zooKeeper.close();
    }
}

etcd Distributed Locks

etcd provides the etcdctl lock command and a gRPC locking API. The protocol uses a compare-and-swap operation to claim a lock, with automatic TTL extension to prevent stale locks. The following demonstrates the concept:

public class EtcdDistributedLock implements AutoCloseable {
    private final etcdClient client;
    private final String lockKey;
    private final String holderId;
    private Lease lease;
    private long lockRevision;
    private boolean acquired = false;
    
    public boolean acquire(Duration timeout) {
        // Create a lease with TTL
        lease = client.leaseClient().grant(300).get();
        
        // Try to acquire the lock using theTxn compare-and-swap
        // The lock is held by the key with the lowest revision number
        while (true) {
            try {
                // Check if we can acquire directly
                TxnResponse txn = client.txnClient().txn(
                    Op.valueCompare(
                        KeyValue.from(lockKey, getCurrentHolder(lockKey)),
                        Compare.CompareResult.EQUAL,
                        ByteSequence.from("")
                    ),
                    Op.put(lockKey, ByteSequence.from(holderId),
                        PutOption.builder().withLeaseId(lease.getId()).build())
                ).commit();
                
                if (txn.isSucceeded()) {
                    lockRevision = getCurrentRevision(lockKey);
                    acquired = true;
                    return true;
                }
                
                // Watch for lock release
                watchForRelease();
                
            } catch (Exception e) {
                // Handle errors
            }
        }
    }
    
    public void release() {
        if (acquired) {
            client.delete(lockKey);
            client.leaseClient().revoke(lease.getId());
            acquired = false;
        }
    }
}

Consul Lock

Consul provides a distributed lock implementation through its KV store. The lock uses a sessions mechanism that provides TTL and automatic release. The following demonstrates the pattern:

public class ConsulDistributedLock implements AutoCloseable {
    private final ConsulClient consulClient;
    private final String lockPath;
    private final String holderId;
    private Session session;
    private boolean acquired = false;
    
    public boolean acquire(Duration timeout) {
        // Create a session with TTL
        session = consulClient.sessionClient().create(
            SessionCreateRequest.builder()
                .name(lockPath)
                .ttl((int) timeout.getSeconds() + "s")
                .build()
        ).get();

        while (true) {
            LockAcquireResponse response = consulClient.kvClient().acquireLock(
                LockAcquireRequest.builder()
                    .key(lockPath)
                    .session(session.getId())
                    .value(holderId.getBytes())
                    .build()
            );
            
            if (response.isAcquired()) {
                acquired = true;
                return true;
            }

            // Implementation watches for key modifications
        }
    }

Lease-Based Lock Implementation

Many production systems implement lease-based locking, where locks are automatically released after a configurable TTL. This approach handles client failures gracefully—if a holder crashes, its lock eventually expires and other clients can acquire it.

The trade-off is that TTL must be chosen carefully. Short TTLs improve responsiveness but increase the risk of premature lock expiration during slow operations or network hiccups. Long TTLs provide safety but delay recovery when holders actually fail.

The following lease-based implementation pattern is common across many distributed lock systems:

public class LeaseBasedLock {
    private final LockBackend backend;
    private final String lockName;
    private final String holderId;
    private final Duration lockTTL;
    private volatile long expirationTime;
    private ScheduledFuture extendTask;
    
    public boolean acquire() {
        boolean acquired = backend.tryAcquire(lockName, holderId, lockTTL);
        if (acquired) {
            expirationTime = System.currentTimeMillis() + lockTTL.toMillis();
            startExtensionTask();
        }
        return acquired;
    }
    
    private void startExtensionTask() {
        extendTask = scheduler.scheduleAtFixedRate(
            () -> {
                if (isExpired()) {
                    // Lock expired, stop extending
                    return;
                }
                
                // Extend the lock before it expires
                Duration remaining = Duration.ofMillis(
                    expirationTime - System.currentTimeMillis());
                
                if (remaining.compareTo(lockTTL.dividedBy(2)) > 0) {
                    // Plenty of time remaining
                    return;
                }
                
                boolean extended = backend.extend(
                    lockName, holderId, lockTTL);
                
                if (extended) {
                    expirationTime = System.currentTimeMillis() 
                        + lockTTL.toMillis();
                }
            },
            lockTTL.dividedBy(3).toMillis(),
            lockTTL.dividedBy(3).toMillis(),
            TimeUnit.MILLISECONDS
        );
    }
    
    public void release() {
        if (extendTask != null) {
            extendTask.cancel(false);
        }
        backend.release(lockName, holderId);
    }
}

Redisson: Production-Grade Distributed Locks

Redisson provides a robust Java implementation of distributed locks built on Redis. It implements the Redlock algorithm (with improvements) and provides additional features like fair locks, multi-lock support, and async operations.

The following demonstrates Redisson's lock API:

public class RedissonDistributedLock {
    private final RedissonClient redisson;
    
    public void executeWithLock(String lockName, Runnable action) {
        RLock lock = redisson.getLock(lockName);
        
        // Try to acquire, wait up to 10 seconds, hold lock for 30 seconds
        boolean acquired = lock.tryLock(10, 30, TimeUnit.SECONDS);
        
        if (!acquired) {
            throw new LockAcquisitionException(
                "Could not acquire lock: " + lockName);
        }
        
        try {
            action.run();
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    public void executeWithFairLock(String lockName, Runnable action) {
        // Fair lock ensures FIFO ordering
        RLock fairLock = redisson.getFairLock(lockName);
        
        fairLock.lock();
        try {
            action.run();
        } finally {
            fairLock.unlock();
        }
    }
    
    public void executeWithReadWriteLock(String lockName, 
            Runnable writeAction, Runnable readAction) {
        RWLockAsync rwLock = redisson.getReadWriteLockAsync(lockName);
        
        // Separate read and write operations
        RLocker writeLocker = rwLock.writeLock();
        RLocker readLocker = rwLock.readLock();
        
        writeLocker.lock();
        try {
            writeAction.run();
        } finally {
            writeLocker.unlock();
        }
    }
}

Redisson also implements the Redlock algorithm, which attempts to acquire locks from multiple Redis instances to reduce the impact of individual node failures:

public boolean tryRedLock(String resource, Duration waitTime, 
        Duration leaseTime) {
    RLock[] locks = new RLock[redisNodes.length];
    
    for (int i = 0; i < redisNodes.length; i++) {
        locks[i] = redissonNodes[i].getLock(resource);
    }
    
    return redisson.getMultiLock(locks)
        .tryLock(waitTime.toMillis(), leaseTime.toMillis(), 
            TimeUnit.MILLISECONDS);
}

Fencing Tokens

A subtle but critical problem with distributed locks is handling a scenario where a lock holder is suspected to be dead but actually isn't—it is slow due to GC pause or network latency. The lock may be released and acquired by another node, and now both nodes hold the lock concurrently.

Fencing tokens solve this problem by requiring lock holders to present a monotonically increasing token with each operation. The resource server validates the token and rejects operations with stale tokens:

public class FencedLock {
    private final LockBackend backend;
    private long currentToken;
    
    public long acquireWithFence(String lockName) {
        long token = backend.acquireFenced(lockName);
        currentToken = token;
        return token;
    }
    
    public void executeWithFence(String lockName, String resource, 
            ThrowingAction action) {
        long token = acquireWithFence(lockName);
        
        try {
            // Pass token to resource operation
            action.executeWithToken(token);
        } catch (StaleTokenException e) {
            // Token rejected, lock was stolen
            handleStaleToken(lockName);
        }
    }
}

The resource operation includes the token:

public class ProtectedResource {
    public void update(String data, long fenceToken) {
        synchronized (this) {
            if (fenceToken < lastSeenToken) {
                throw new StaleTokenException(
                    "Operation rejected: fence token " + fenceToken + 
                    " is older than " + lastSeenToken);
            }
            lastSeenToken = fenceToken;
            // Proceed with update
        }
    }
}

Best Practices for Distributed Locking

Implementing distributed locks correctly requires attention to several key concerns. The following best practices help avoid common pitfalls.

Always use a TTL on locks. Even with careful release handling, client crashes can leave locks held indefinitely. TTL ensures eventual recovery. Choose TTL values that accommodate your longest expected operation plus a safety margin.

Implement lock extension for long-running operations. If operations may take longer than the initial TTL, implement automatic extension. This keeps the lock held while the operation is in progress while still providing failure recovery.

Use fencing tokens for resources that require strict mutual exclusion. Without fencing, concurrent lock holders can corrupt shared state. Fencing ensures that only the latest holder's operations succeed.

Release locks in finally blocks to ensure cleanup. Use try-finally or equivalent patterns to guarantee release even when exceptions occur. Consider using weak references or other mechanisms to detect and clean up leaked locks.

Monitor lock acquisition latency, contention, and failure rates. High contention may indicate design problems. Failed acquisitions may indicate timeout misconfiguration or system overload.

Test failure scenarios explicitly. Simulate network partitions, node crashes, and GC pauses to verify lock behavior under adverse conditions. Ensure the system makes progress even when failures occur.

Conclusion

Distributed locking enables coordination in systems that span multiple machines, providing essential mutual exclusion guarantees for shared resources. From simple database-based locks to sophisticated coordination service implementations, the choice depends on application requirements, scale, and failure tolerance.

The key to successful distributed locking is understanding its limitations. No lock implementation can provide perfect safety under all failure scenarios. Applications must be designed to handle lock acquisition failures, timeout expiration, and the window of potential concurrent access that exists in any distributed system.

Modern implementations like Redisson, ZooKeeper, and etcd provide production-grade building blocks. When combined with careful design, proper monitoring, and thorough testing, distributed locks provide reliable coordination for even the most demanding enterprise applications.
